# Аудит рецептов и заявок

Дата проверки: 11.09.2026

## Что было не так

- В локальной базе было только 4 блюда, поэтому планировщик быстро повторял одни и те же варианты.
- В `products.json` были дубли и шумные/неаккуратные названия, из-за чего точное сопоставление ингредиентов было менее надёжным.
- Два старых рецепта ссылались на отсутствующее изображение.
- Форма рецепта подсказывала ввод `1 шт.`, хотя внутренний формат рецептов использует граммы. Старый парсер мог принять `1 шт.` за 1 грамм.
- Одобренный пользовательский рецепт без вручную введённых калорий получал `0 ккал` в объекте рецепта и не участвовал в обычном планировщике.
- Серверная Edge Function принимала заявки всех типов, но проверяла только общую структуру, а не обязательные поля конкретного типа.
- Письма о новых заявках вообще не отправлялись: `submit-content` только сохранял запись в Supabase.
- В инструкции был указан другой Supabase project ref, не совпадающий с `docs/js/submission-config.js`.
- В manifest упоминался `.env.example`, но самого файла в архиве не было, а `.gitignore` исключал `.env.*` без исключения для примера.

## Что изменено

- 30 локальных рецептов вместо 4.
- Добавлены домашние блюда: сырники, шарлотка, макароны по-флотски, запеканка, блины, оладьи, драники, плов, борщ, щи, рассольник, голубцы, тефтели и другие.
- Добавлены базовые продукты, необходимые новым рецептам.
- Удалены дубли названий продуктов и исправлены проблемные пробелы/пунктуация.
- Добавлены бытовые синонимы для планировщика и более консервативная обработка молочных аллергенов.
- Планировщик теперь предпочитает новое подходящее блюдо повтору уже использованного и разрешает меньшую порцию для перекусов.
- Для одобренных пользовательских рецептов БЖУ автоматически вычисляется по известным ингредиентам, если пользователь не заполнил его вручную и все ингредиенты можно однозначно сопоставить.
- Парсер ингредиентов корректно понимает г/кг/мл и больше не превращает `1 шт.` в 1 грамм.
- В форме рецепта появились отдельные поля белков, жиров и углеводов.
- `submit-content` теперь валидирует обязательные поля отдельно для продукта, рецепта, статьи и мифа.
- После успешного сохранения заявки `submit-content` умеет отправлять владельцу письмо через Resend.
- Контакт автора и комментарий модератору остаются закрытыми полями и не попадают в публичный payload.
- В письме есть тип заявки, ID, заголовок, автор, контакт, все поля и ссылка на панель модерации.
- Для письма используется `Idempotency-Key`, чтобы повтор одного HTTP-запроса не плодил одинаковые уведомления.
- В центре заявок добавлена отдельная карточка для мифа/утверждения.
- Исправлен Supabase project ref в инструкции: `qekkfmsiwocrxbwyuwsa`.
- Добавлен `.env.example` и GitHub Actions quality workflow.

## Что нужно настроить один раз для почты

Заполни локальный `.env` по `.env.example`:

```text
RESEND_API_KEY=...
SUBMISSION_FROM_EMAIL="Healthy Food <notifications@your-domain.example>"
SUBMISSION_NOTIFY_EMAIL=you@example.com
SUBMISSION_SITE_URL=https://dafi3134.github.io/foods
```

Затем:

```bash
supabase link --project-ref qekkfmsiwocrxbwyuwsa
supabase secrets set --env-file .env
supabase functions deploy submit-content
```

Для production у Resend должен быть подтверждён домен отправителя.
